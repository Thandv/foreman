Put a new check here as a `.ts` file instead of editing `scripts/verify.sh`. After the suite, `verify.sh` runs each `scripts/checks/*.ts` in sorted order with `node <file>`; a check that exits non-zero fails verify and the output names the file. When the suite itself failed, its exit status is the one `verify.sh` returns; otherwise it is the first failing check's. Each check is stopped, with anything it started, after `VERIFY_CHECK_TIMEOUT_SECS` seconds (default 300) and then fails as `verify: FAIL (check <file> timed out after <n>s)`.

`no-raw-db.ts` ratchets raw ledger SQL: outside `src/queue.ts` and `src/db.ts`, each src file's `.prepare`/`.exec` calls on a `.db` (or on a local bound to `new DatabaseSync`), and its `new DatabaseSync` openers, must equal its entry in the check's `ALLOW`. A new site fails; so does an entry higher than the file's count, so the change that removes a site lowers its entry. It finds the sites with the TypeScript parser, so a chain split over lines counts and a comment does not, and classes each as a read or a write (INSERT/UPDATE/DELETE/REPLACE/DDL/VACUUM, or non-literal SQL not read at once with `.get`/`.all`/`.iterate`) and each opener as read-only (`{ readOnly: true }`) or writable. It prints the totals, among them `raw writes outside queue: N` and `writable openers outside queue: N`.
